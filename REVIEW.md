# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints).

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Used naive string `replace` constructing shift start on `punch_in`'s calendar date (fails for overnight shifts / UTC-IST offsets). Used `minutes > 10` which caused `09:40:01` (10.016 mins elapsed) to evaluate `int(10.016) = 10`, `10 > 10` -> `False`, returning 0 late minutes instead of 10. | Call with `09:40:01` for a `09:30` shift: returned 0 instead of 10. Call with an overnight shift punch-in after midnight: computed wrong offset. | Calculated difference in seconds in IST against scheduled start on the attendance date (`YYYY-MM-DD`). Checked `diff_sec > 600` (strictly > 10 mins) and returned `int(diff_sec // 60)`. |
| 2 | `compute_work_hours` | Used Python's builtin `round(..., 2)` which performs banker's rounding (round half to even) instead of half-up rounding (R4). | Calling `compute_work_hours` with elapsed time resulting in `2.675` hours returned `2.67` instead of `2.68`. | Implemented `round_half_up` helper function using `decimal.Decimal` with `ROUND_HALF_UP`. |
| 3 | `compute_overtime` | Constructed shift end on `date_str` without accounting for overnight shifts where `shift_end <= shift_start` (shift end falls on the next calendar day). Returned `max(0, int(...))` without enforcing the 30-minute minimum threshold (R3). | Overnight shift (22:00 - 06:00) punching out at 06:40 next day calculated negative duration. Punching out 15 minutes after shift end returned 15 instead of 0. | Added overnight check (`shift_end <= shift_start` adds 1 day to scheduled end in IST). Counted overtime only if `diff_sec >= 1800` (>= 30 mins). |
| 4 | `POST /employees` | Used check-then-insert (`if db.employees.find_one(...)`) causing race conditions under concurrency. Stored naive `datetime.now()` instead of UTC datetime and failed to return epoch ms for `created_at`. Failed to validate `shift_start != shift_end`. | Concurrent duplicate requests both passed `find_one` check. `created_at` in response was not epoch ms integer. Allowed creating employee with `shift_start == shift_end`. | Enforced unique database index on `emp_code`, handled `DuplicateKeyError` (409). Validated `shift_start != shift_end` in Pydantic model. Stored UTC datetime and returned epoch ms. |
| 5 | `GET /employees` | Pagination skip was `skip = page * page_size`, skipping the first page of items. Counted total using `db.employees.count_documents({})`, ignoring the `department` filter. | `GET /employees?page=1` skipped first 20 employees. `GET /employees?department=Engineering` returned `total` equal to entire collection count. | Fixed skip to `(page - 1) * page_size` and total count to `db.employees.count_documents(q)`. |
| 6 | `POST /attendance/punch-in` | Used check-then-insert `if db.attendance_logs.find_one(...)` causing race conditions. Did not verify employee exists (spec requires 404). Used naive `datetime.fromtimestamp` without timezone handling. Calculated date as `ts.date().isoformat()` missing R1 overnight shift rule. Returned forbidden `"id"` field. Allowed non-presence status values. | Two concurrent punch-ins created duplicate records. Punching in for unknown employee returned 201 instead of 404. Overnight punch-in assigned wrong date. Response contained `id` field. | Created unique compound index `(emp_code, date)` and handled `DuplicateKeyError` (409). Verified employee existence (404). Applied `get_attendance_date` helper for R1. Validated presence status (`PRESENT`, `WFH`, `ON_DUTY`). Formatted response without `id`. |
| 7 | `GET /attendance` | Loaded entire collection into Python memory (`list(db.attendance_logs.find(q))`) and sorted in Python, violating 100,000 document performance requirement. Pagination was in-memory. Injected forbidden `"id"` field. Did not validate `date_from > date_to`. | Server memory spiked on large datasets. Passing `date_from=2026-07-10&date_to=2026-07-01` returned 200 instead of 422. Items contained `id` key. | Delegated sorting (`.sort([("date", -1), ("emp_code", 1)])`), pagination (`.skip().limit()`), and counting (`count_documents(q)`) to MongoDB. Added 422 validation for `date_from > date_to`. |
| 8 | General API Boundary / Instants | Instants were not validated or formatted as integer epoch milliseconds (`int64`). Subseconds were not truncated before calculations (R1). | API responses contained datetime strings/objects instead of epoch ms ints. Passing float or out-of-range epoch ms was accepted. | Added `validate_epoch_ms` validator checking range `[100000000000, 4102444800000]` and integer type (rejecting floats/strings with 422). Truncated subseconds in `epoch_ms_to_datetime_utc`. |

## What was examined and decided was NOT a defect
- **`GET /health` endpoint structure**: The basic path `/health` and returning `{"status": "ok"}` on success matched the contract. We enhanced it to execute `db.command("ping")` and return `503` if MongoDB is unreachable, per section 7 spec.
- **Pydantic model usage for input parsing**: Using Pydantic models for request body deserialization is standard in FastAPI and correctly handles JSON schema parsing when proper field constraints and validators are attached.
